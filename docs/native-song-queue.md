# B 站点歌队列与 SPlayer 下一首调度

2026-11-11：正式应用已接入此前验证过的 B 站账号、WSS 和弹幕处理逻辑，点歌改用 SPlayer 原生播放列表。自动化使用模拟平台与宿主，真实房间到原生入队的闭环仍需人工验收；此前 `playTrack` 实测不等于本次 `addToQueue` 已真机通过。

2026-11-12：应用 v0.1.1 修复 WSS 首节点端口不可达时的连接恢复，增加有限备用节点 / 443 回退及设置页「直播连接诊断」。已在真实房间验证 2245 超时后通过 443 完成游客直播认证，详见 [修订记录](releases.md)。插件仍为 0.3.0。

2026-11-12 当前版本为 **应用 v0.2.0 / 插件 0.4.0**，按用户新要求，后端维护观众点歌顺序，每次只预放一首到 SPlayer“下一首”，确认其开始播放后再安排后续请求。以下说明以当前实现为准，替代旧版批量追加队尾。

## 启动与使用

1. 在根目录执行 `npm ci`、`npm run build`、`npm start`。
2. 启动新版后端，将 `dist/splayer-live-lyrics.js` **0.4.0** 重新导入 SPlayer-Next 并启用。沿用原插件 ID，保留 `network` / `control`。歌词仍支持 API 4，点歌需要 API 5。新插件与新后端先确认调度版本；旧插件不能领取新版任务，新插件也不领取旧版后端任务。
3. 打开 `http://127.0.0.1:19633/`，在「B 站观众点歌」扫码或导入 Cookie，检查接收账号，再输入房间号并用账号模式连接。
4. 选定音源，勾选「启用点歌处理」并应用。默认只接受有可靠 UID 的弹幕；身份缺失或受限时是否允许可由主播明确开启。游客模式仅查看弹幕。
5. 观众发送 `点歌 晴天`。设置页显示当前点歌、已安排下一首、排队记录及处理历史；展开可查看 SPlayer 实际列表，也可手动输入关键词验证。

设置、待处理记录、B 站凭据均仅保存在服务内存中。重启后需重新登录、连接和启用点歌；已加入 SPlayer 的歌曲仍由 SPlayer 自己管理，不会自动重新添加。独立实验插件使用不同端口，不需要与正式插件同时启用。

## 排队行为

- 仅解析去掉首尾空白后的 `点歌 + 空白 + 非空关键词`；关键词最多 200 字符。歌曲按各请求收到时的音源设置搜索第一页第一项，不重排、不替补。
- 后端最多保留 50 首排队 / 执行 / 待播点歌，按接收顺序派发。SPlayer 最多提前放入一首尚未开始的点歌，后续请求留在后端，不会因为连续调用“下一首”倒置观众顺序。
- 插件将搜索返回的完整 Track 传给 `addToQueue([track], "next")`，不调用 `playTrack`，不会抢播，也不自动改变随机或循环模式。普通歌单继续播放，到下一首时进入点歌；暂停 / 空闲时添加歌曲不自动开始播放。
- 插件提交前按每页 100 首读取完整列表，保存来源与 ID 的计数。提交后核对整体只增加目标曲目一项，且它位于当前曲目的下一项或已经成为当前项；其他曲目顺序变化不导致误报。扫描限制为 10,000 首，提交前扫描最多 6 秒，提交后核对总计最多 10 秒；页面不完整、总数或当前索引读取期间变化时不伪造确认。
- 本机 SPlayer 实现会按 ID 跳过已有歌曲，接口的 `count` 仅为提交数量。已有同来源曲目显示「已在播放列表」，不调用入队、不移动位置，继续后续请求；相同 ID 的其他来源曲目明确失败。当前文档化接口不能移动或删除已有项，因此不能保证重复歌曲按新点歌位置重新播放。
- 「已安排下一首」只证明入队与位置核对完成，不表示音源可播放。后端等待活动歌词会话上传、通过序号和曲目修订校验的播放采样；仅当目标来源 / ID 与当前曲目相同且状态为 `playing` 才解除该待播项并安排下一首。暂停、无关切歌、歌词行变化与推算时长不会提前推进。歌曲开始先于结果回报时，也会核对最近有效采样，不漏掉推进。
- 原生队列约每 2 秒同步一次，显示当前曲目及之后最多 49 首。主播在 SPlayer 中的排序、移除和切歌会在随后同步反映。列表过长时，完整内容在 SPlayer 查看。
- 开启随机或单曲循环时显示提示，实际播放仍遵循 SPlayer。点歌会核对下一首位置；单曲循环、手动跳过或移除待播项可能使后端持续等待。主播核对后可「解除待播等待，继续后续点歌」，此操作仅解除该项等待，不删除播放器歌曲，也不会重放该项。操作带当前待播命令 ID，旧页面不能误解除另一首。
- 尚未派发的点歌可在设置页取消。已入队歌曲的移除 / 排序在 SPlayer 中完成；当前文档化插件 API 未提供队列移除和重排，网页不伪造这些操作。

## 故障与边界

命令使用 `commandId`、执行插件 `sessionId`、后端 `serverId` 及每次派发的 `leaseId` 关联。搜索结束、提交入队之前再次向后端核对命令有效性。关闭处理、租约过期、后端或插件会话更换均会阻止尚未提交的入队。

搜索无结果、已有曲目或提交前检查失败不阻塞下一条。入队调用后异常、核对失败、45 秒内未收到执行结果或执行中会话被替换，均视为结果不确定：不重复派发该请求，暂停后续处理，主播核对 SPlayer 列表后点击「继续处理」。结果上传失败只重试结果，不再次执行入队。迟到结果不能覆盖已结算状态。诊断仅保存核对前后总数及目标计数，不记录凭据或完整宿主异常。

插件播放采样超过 6 秒未更新时不派发新任务；待播项保留，恢复后继续等实际播放。插件重新导入时仍保留已确认待播项，防止把新的“下一首”插在它前面；活动执行则按不确定处理。关闭点歌不删除已安排的歌曲，开启后按后端剩余顺序继续。

如果命令响应丢失，插件可能尚未拿到命令，后端仍按不确定处理。发生不确定状态后，需要主播检查原生列表并决定是否重新提交该首点歌；「继续处理」只释放后面的请求。

入队前的校验与宿主调用之间存在很短的间隔，已经交给宿主的调用无法撤销。命令超时和会话切换均不承诺能取消宿主已经收到的动作。后端重启不会恢复或重放内存命令。

弹幕优先按房间与消息 ID 去重，缺失 ID 时只在有发送者 UID 和发送时间的情况下使用包含正文的组合去重。缺少可靠字段时不按昵称 / 文本合并，避免不同观众点同曲被吞掉。受限身份不伪造 UID。

账号和房间连接沿用已验证的同会话鉴权；游客使用新 CookieJar。凭据不写入文件，不进入 OBS WebSocket；输出页仍只接收歌词、播放和样式状态。B 站断线需手动重连，已接收的请求继续处理；关闭「启用点歌处理」可暂停待处理任务，已经发给 SPlayer 的歌曲不受影响。服务不会向直播间发送回复。

## 接口与模块

| 边界 | 实现 |
| --- | --- |
| B 站 API / QR / WSS | `backend/bilibili/`；从已验证实验提升到正式模块，正式构建不依赖实验目录 |
| 规范化弹幕 → 指令 | `backend/requests.mjs`：解析、去重、身份、上限、FIFO、执行租约及结果 |
| 管理状态 | `GET /api/requests`，不混入 OBS 输出 |
| 管理操作 | `POST /api/requests/{config,add,cancel,resume,release}`、`POST /api/bilibili/login/{qr,cancel,check,cookie}`、`POST /api/bilibili/logout`、`POST /api/bilibili/room/{connect,disconnect}` |
| 插件执行 | `POST /api/plugin/commands/{poll,check,report}`、`POST /api/plugin/queue`，要求活动歌词插件会话和协议头 |
| 原生入队及快照 | `plugin/requests.js`，与歌词采样独立循环；只使用文档化插件接口 |
| 网页 | `web/requests.mjs`，真实队列、待处理和历史分别显示；内容使用文本节点渲染 |

管理 POST 需要同源和 `X-SPlayer-Live-Management: 1`，插件需要 `X-SPlayer-Live-Protocol: 1`；仅监听回环地址，不开启 CORS。没有自动平台登录或开机后自动点歌。

## 验证

`npm test` 包含原有歌词测试及正式 B 站模块、命令生命周期、实际构建插件的集成测试。覆盖扫码 / Cookie / 游客、认证心跳与压缩包、身份、去重、原生入队、保留完整 Track、结果回报丢失、入队异常、关闭处理、租约过期及搜索期间歌词同步。

39 项测试通过，新增真实构建插件连续三首、暂停与无关切歌不推进、469 首随机列表中的已有曲目、顺序变化、确认回包但未插入、错误插入位置、截断分页、旧插件不领取、播放先于回报、失联与手动解除等待。Edge 设置页验证通过。

真机先在普通歌单播放时手动提交三首不在列表的歌曲：确认仅 A 插为下一首，A 开始后插 B，B 开始后插 C；三首结束后继续原歌单。再测试已有歌曲明确跳过、暂停、手动跳过 / 解除等待，以及真实房间连续点歌。没有完成这些操作前，不将模拟结果写成真实 B 站点歌验收通过。
